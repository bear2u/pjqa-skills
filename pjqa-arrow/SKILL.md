# A — Arrow, 화살표 하나만 바꾸기

## 목적

새 제품은 세상을 새로 만들지 않는다. 사람들이 이미 하고 있는 흐름의 한 구간만 바꾼다. 이 단계는 "어느 구간을 바꾸는가"를 정확히 하나로 못 박아 MVP의 경계를 만든다.

## 입력

- `02-journeys.md` (진짜 문제·바닥), `03-quadrant.md` (채택 후보)
- Q 산출물이 없으면 채택 후보를 사용자에게 확인하고 진행한다.

## 워크플로우

1. **AS-IS 흐름을 그린다.** 제품이 없던 지금, 사람들이 이 문제를 어떻게 처리하는지 4~6단계로.
   - 규칙: 단계는 전부 "기존 도구·행동"으로 적는다 (예: 지인에게 부탁 → 카톡으로 일정 조율 → 돌봄(소식 없음) → 끝나고 카톡 보고 → 계좌이체). 앱 화면 이름이 나오면 잘못 그린 것이다.
   - J의 주인공 중 주 사용자의 행동 흐름으로 그린다. 나머지 주인공의 행동은 관련 단계에 괄호로 붙인다.
2. **바닥이 있는 구간을 표시한다.** J의 주 바닥이 AS-IS의 어느 화살표(단계와 단계 사이)에 있는지 찾는다. 보통 바닥은 단계 안이 아니라 **단계와 단계 사이의 구간**에 있다 (예: "돌봄 → 보고" 사이의 무소식 구간).
3. **바꾸는 화살표를 정확히 1개 고른다.** 판정 기준:
   - 그 화살표가 J의 주 바닥과 겹치는가.
   - Q에서 채택한 기능이 그 구간을 바꾸는 도구인가.
   - 두 기준이 같은 화살표를 가리키면 확정. 다르면 이유를 적고 사용자에게 확인받는다 — 임의로 합치지 않는다.
4. **나머지 구간은 "그대로 둔다"고 명시한다.** 바꾸지 않는 구간 각각에 기존 방식을 유지한다는 것을 적는다. 이 선언이 MVP를 작게 유지하는 장치다.
5. **바꾼 뒤의 흐름(TO-BE)을 한 줄로 대조한다.** AS-IS와 TO-BE를 나란히 적되, 달라지는 건 그 화살표 하나뿐이어야 한다.

## 산출물 계약 — `04-arrow.md`

```markdown
# 화살표 — <아이디어명>

## AS-IS (지금 흐름)
1. ... → 2. ... → ... (4~6단계)

## 바꾸는 화살표 (딱 1개)
<단계 A> → <단계 B> 구간 — <지금은 어떻게 비어/막혀 있는가>
근거: J의 주 바닥 <구간>과 겹침 / Q 채택 기능 <이름>이 이 구간을 바꾼다

## 그대로 두는 구간
- <구간> — 기존 방식 <무엇> 유지

## TO-BE (바꾼 뒤)
1. ... → (바뀐 구간) → ... — 달라지는 건 이 구간뿐
```

## 품질 게이트

- 바꾸는 화살표가 2개 이상이면 실패. 하나만 남기고 나머지는 2차로 보낸다.
- 화살표의 근거에 J의 바닥이 인용되지 않으면 실패.
- AS-IS에 자사 제품·앱 기능이 등장하면 실패. 지금 사람들이 실제로 하는 행동만 적는다.

## 규칙

- "전체를 자동화" 같은 큰 그림으로 새지 않는다. 이 단계의 미덕은 작게 자르는 것이다.
- 화살표 하나의 변화가 작아 보여도, 바닥과 겹치면 그것이 MVP의 핵심이다. 크기로 재판하지 않는다.
